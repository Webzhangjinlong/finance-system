01

项目概览与技术栈定稿

确认开发目标、范围边界与最终技术选型

1.1 开发目标与范围

  • 交付一套前后端分离的 Web 财务管理系统，覆盖财务管理、合同管理、人事管理三大模块；
  • 核心目标：业财一体化——业务单据（报销/合同收付款/工资）审批后自动生成记账凭证；
  • 范围：PC 端优先，移动端（H5 查看待办/工资条）作为二期；
  • 不包含（二期可选）：发票税局验真对接、银行代发对接、电子签章、绩效管理。

02

总体架构与工程结构

前后端分离 + 后端按业务域分包（模块化单体），便于拆分与维护

2.1 工程结构（Git 仓库）

finance-system/                        # 项目根（monorepo）
├── finance-web/                       # 前端 Vue3 工程
│   ├── src/
│   │   ├── api/                       # 接口封装（按模块）
│   │   ├── views/                     # 页面（system/finance/contract/hr）
│   │   ├── router/  stores/  utils/   # 路由 / Pinia / 工具（axios、权限指令）
│   │   └── components/                # 通用组件（表单、审批弹窗、科目树）
│   └── package.json
├── finance-server/                    # 后端 Spring Boot 工程
│   ├── finance-common/                # 公共：统一返回、异常、工具、常量
│   ├── finance-framework/             # 框架：Security/JWT、RBAC、Redis、数据权限
│   ├── finance-system/                # 系统管理：用户/角色/菜单/字典/日志
│   ├── finance-finance/               # 财务域：科目/凭证/账簿/报销/收付款/报表
│   ├── finance-contract/              # 合同域：台账/审批/收付款计划/提醒
│   ├── finance-hr/                    # 人事域：员工/考勤/薪酬/社保
│   └── finance-workflow/              # 审批流（Flowable 封装）
├── deploy/                            # Docker Compose、Nginx 配置、SQL 初始化
└── docs/                              # 设计/开发文档、接口文档

2.2 后端分层（每个业务域内部）

Controller（接口）→ Service（业务）→ Mapper（数据访问），跨域调用走 Service 层接口，避免循环依赖；凭证生成等跨域逻辑放在 finance-finance 内的「凭证引擎」组件，对外提供事件/接口。

Controller：校验 + 参数 + 权限注解 Service：业务规则 + 事务 Mapper：MyBatis-Plus + XML 复杂查询 Domain：实体 + 枚举 + DTO/VO

2.3 关键架构决策

  • 模块化单体：不拆分微服务，降低运维成本；按业务域分包，后续可平滑拆出独立服务；
  • 资金类操作强事务：收付款、凭证生成、薪酬发放用 @Transactional + 幂等键防重复；
  • 业务事件解耦：单据审批通过 → 发布事件 → 凭证引擎监听生成凭证，避免强耦合；
  • 数据权限：通过 MyBatis-Plus 拦截器按角色数据范围（全部/本部门/本人）自动注入过滤条件。

数据库设计（PostgreSQL 16）

核心表 25+ 张，金额统一 NUMERIC(18,2)，统一公共字段与逻辑删除

3.1 公共设计约定

  • 金额：一律 NUMERIC(18,2)，禁止用 float/double；
  • 主键：BIGINT GENERATED ALWAYS AS IDENTITY；
  • 公共字段：create_by / create_time / update_by / update_time / deleted（逻辑删除）；
  • 时间：TIMESTAMP WITH TIME ZONE；
  • 辅助核算：凭证分录表带可空外键 department_id / customer_id / supplier_id / contract_id，支持多维统计。

CREATE TABLE fin_voucher (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    voucher_no    VARCHAR(32)  NOT NULL,          -- 凭证号（期间+序列）
    period        VARCHAR(7)   NOT NULL,          -- 会计期间 2026-09
    voucher_date  DATE         NOT NULL,
    summary       VARCHAR(200),
    total_debit   NUMERIC(18,2) NOT NULL DEFAULT 0,
    total_credit  NUMERIC(18,2) NOT NULL DEFAULT 0,
    status        VARCHAR(20)  NOT NULL DEFAULT 'DRAFT', -- DRAFT/AUDITED/BOOKED/REVERSED
    source_type   VARCHAR(30),                    -- 来源：MANUAL/EXPENSE/CONTRACT/SALARY
    source_id     BIGINT,                         -- 来源单据
    create_by     BIGINT, create_time TIMESTAMPTZ,
    update_by     BIGINT, update_time TIMESTAMPTZ,
    deleted       SMALLINT DEFAULT 0,
    CONSTRAINT uk_voucher_period_no UNIQUE (period, voucher_no),
    CONSTRAINT ck_voucher_balance CHECK (total_debit = total_credit)
);

06

核心难点实现思路

五个决定系统质量的关键点，先讲清思路再动手

6.1 凭证生成引擎（单据→凭证）

  1. 规则表 fin_voucher_rule：配置「单据类型 + 费用类型 → 借方科目 / 贷方科目 / 辅助核算项」；
  2. 事件驱动：业务单据审批通过 → 发布 BusinessDocApprovedEvent（含 sourceType/sourceId/金额/辅助信息）；
  3. 引擎生成：监听事件 → 查规则 → 组装分录 → 写入凭证草稿（status=DRAFT），来源字段回填；
  4. 幂等：以 source_type + source_id 建唯一约束，防止重复生成；
  5. 人工兜底：未配置规则或特殊情况走手工凭证，不阻塞业务。

6.2 凭证号连续性与结账

  • 凭证号 = 期间 + 序列，用 seq_voucher_no 序列保证并发下不重号；
  • 结账：校验（借贷平衡、未过账凭证、资产=负债+权益）→ 锁定期间（期间表 is_closed）→ 已结账期间凭证只读；
  • 改错：已过账凭证不允许直接修改，走红字冲销 + 蓝字重录，保留审计痕迹。

6.3 审批流（Flowable）与业务解耦

  • 流程定义按业务配置（合同审批、报销审批、付款审批），用网关按金额分级路由；
  • 审批动作通过统一 WorkflowService.complete()，回调更新业务单据 status 并发布事件；
  • 员工/角色变化不重开流程：任务节点绑定「角色 + 数据范围」，实时取当前审批人。

6.4 收付款与合同联动

  • 合同收付款计划到期 → 生成应收应付 → 出纳登记收付款 → 核销应收应付并回写计划状态 → 凭证引擎生成资金凭证；
  • 核销规则：支持部分核销、多单核销一笔，账龄按「剩余未核销金额 + 到期日」计算。

6.5 定时提醒任务

任务频率逻辑
合同到期提醒每日到期前 30 天 / 已到期未处理 → 站内消息
收付款节点提醒每日计划日期前 7 天 → 提醒责任人
逾期应收扫描每日账龄超期 → 更新预警状态 + 消息

开发排期与里程碑

按「2 后端 + 1 前端 + 0.5 测试」的 1 个团队估算（约 4 个月），可按实际人手等比调整

阶段 0 · 基建（第 1–2 周）

脚手架 · 环境 · 数据库初始化
  • 前后端脚手架、Git 仓库、CI（编译/静态检查）
  • Docker 环境（PostgreSQL 16 / Redis / MinIO）、建库建表 DDL 落地
  • 统一返回体、异常处理、日志、JWT 登录 + RBAC 框架
  • 里程碑：能登录、菜单按角色渲染

阶段 1 · 系统 + 财务核心（第 3–7 周）

系统管理 · 科目 · 凭证 · 账簿 · 报表
  • 用户/角色/菜单/字典/操作日志、数据权限
  • 科目管理、凭证录入/审核/过账、凭证号序列、账簿查询
  • 期末结账、三大财务报表
  • 里程碑：完成一个月手工记账闭环（MVP 记账）

阶段 2 · 业务单据 + 凭证引擎（第 8–12 周）

报销 · 收付款 · 应收应付 · 凭证映射引擎
  • 费用报销全流程（含审批流接入）
  • 收付款单、应收应付、核销、账龄
  • 凭证映射引擎（规则配置 + 事件 + 自动生成）+ 合同台账/审批/收付款计划
  • 里程碑：报销、合同收付款自动生成凭证（业财主线打通）

阶段 3 · 人事 + 提醒 + 驾驶舱（第 13–16 周）

员工 · 工资 · 考勤 · 定时提醒 · 驾驶舱
  • 员工档案、部门、工资核算与工资条（含自动凭证）
  • 考勤管理、社保公积金（基础）
  • 合同到期/收付款/逾期应收定时提醒；经营驾驶舱
  • 里程碑：三大模块功能齐备

阶段 4 · 联调上线（第 17–18 周）

联调 · 测试 · 数据迁移 · 试运行
  • 端到端联调、安全加固（HTTPS/限流/审计）、性能冒烟
  • 历史数据导入（期初余额、科目、员工 Excel 模板）
  • 试运行 1 个会计期间 → 修复 → 正式上线
  • 里程碑：正式上线

测试方案

财务系统以「数据正确性」为第一质量目标，测试分层设计

8.1 测试分层

层级工具覆盖重点
单元测试JUnit 5 + Mockito凭证生成引擎、金额/个税计算、凭证号序列、映射规则匹配
接口测试Apifox / REST Assured全部 REST API 的正向/异常路径
集成测试Testcontainers（PG）事务回滚、并发凭证号不重号、审批流回调
前端测试Vitest + Vue Test Utils关键表单校验、权限按钮显隐
验收测试人工 + 用例清单按设计方案业务流程逐条走查

8.2 关键测试用例（财务正确性）

  • 凭证录入：借贷不等不允许保存（数据库 CHECK 兜底 + 前端校验）；
  • 凭证号：并发 100 笔同时生成不重号、不跳号；
  • 映射引擎：同一单据重复提交事件不产生第二张凭证（幂等）；
  • 结账：已结账期间凭证不可新增/修改；结账前未过账凭证拦截；
  • 权限：普通员工调用他人工资条接口返回 403；数据权限过滤生效；
  • 报表：三大报表勾稽关系（资产=负债+权益、现金流入流出=净变动）。

部署与运维方案

9.1 部署拓扑

11

多公司（多账套）支持

一套代码、一套数据库（共享库），用公司编码 company_code 区分；公司之间完全独立、互不可见、无合并需求

11.1 设计原则

  • 一套部署：单库单 schema + 一套前后端代码，所有公司共用同一实例；
  • 公司编码区分：所有业务数据统一携带 company_code，作为数据归属的唯一标识；
  • 完全独立：公司之间无业务关系、无合并报表需求；科目、凭证、期间、结账、报表、合同、人事各自独立；
  • 互不可见：非本公司的数据任何角色均不可见（查询强制按 company_code 过滤 + RLS 兜底）。

11.2 公司档案表 sys_company（DDL）

CREATE TABLE sys_company (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    company_code  VARCHAR(20)  NOT NULL,           -- 公司编码，如 A001
    company_name  VARCHAR(100) NOT NULL,           -- 公司名称
    tax_no        VARCHAR(50),                     -- 纳税识别号
    contact       VARCHAR(50),  phone VARCHAR(30), -- 联系人 / 电话
    status        VARCHAR(10)  NOT NULL DEFAULT 'ENABLED', -- ENABLED / DISABLED
    create_by     BIGINT, create_time TIMESTAMPTZ,
    update_by     BIGINT, update_time TIMESTAMPTZ,
    deleted       SMALLINT DEFAULT 0,
    CONSTRAINT uk_company_code UNIQUE (company_code)
);

11.3 company_code 贯穿清单（所有业务表统一新增）

域需加 company_code 的表
系统sys_user（归属公司）、sys_operation_log
财务fin_account_subject、fin_voucher、fin_voucher_entry、fin_period、fin_voucher_rule、fin_expense_claim、fin_expense_item、fin_receivable_payable、fin_payment_receipt、fin_bank_account
合同ct_contract、ct_contract_payment_plan、ct_contract_attachment
人事base_department、hr_employee、hr_attendance、hr_salary、hr_social_security

字段规范：company_code VARCHAR(20) NOT NULL，每张表建 (company_code, …) 联合索引；凭证表唯一约束改为 UNIQUE (company_code, period, voucher_no)。

11.4 关键机制改造

机制多公司改造方案
登录与上下文用户归属公司（sys_user.company_id）；登录后 ThreadLocal 携带 company_code；所有查询自动追加公司过滤
凭证号序列维度 = 公司 + 期间，seq_voucher_no(company_code, period)
期间 / 结账fin_period 带 company_code，各公司独立结账 / 反结账
科目体系每公司一套科目；提供「从模板公司复制科目」一键初始化新公司
数据权限在 全部 / 本部门 / 本人 之上增加「本公司」强制维度，任何角色不可跨公司
RLS 兜底核心财务表启用 PostgreSQL 行级安全（policy 按 company_code），SQL 漏写条件也不串号
审批流Flowable 流程实例带 tenantId = company_code
附件MinIO 对象路径前缀 company_code/，按公司物理隔离

11.5 新增公司初始化流程

  1. 管理员在「公司管理」新增公司档案（编码 / 名称 / 税号）→ 启用；
  2. 复制科目模板（或从已有公司复制科目）→ 录入该公司期初余额；
  3. 创建该公司账号（或给既有用户分配该公司）→ 配置该公司角色 / 数据权限；
  4. 导入部门、员工；配置该公司字典与凭证映射规则（可复用模板）；
  5. 开始独立记账：凭证号、期间结账、报表均按该公司独立运行。
